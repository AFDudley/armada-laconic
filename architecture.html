Architecture — the tier stack

Armada settles private execution on a Nitro rail. The motion is the same everywhere: notes in → normal Nitro → notes out. Value leaves Armada's shielded pool, moves through ordinary Nitro state channels, and returns as shielded notes. Seven tiers, each mapped to existing code where it exists, and marked as a plan where it does not.

non-custodial Ethereum L1-anchored Nitro settlement pool immutable / untouched

Tiers are named in the software-architecture sense (an n-tier stack), not the "Layer 1 / Layer 2" of blockchains. Every claim maps to code on the item registry and the Build plan, with pinned commits and status. This page is the structure; the registry is the status and code location.

The shape of the network — today vs. the plan

The deployed shape is a conventional server-client topology, not a peer-to-peer federation. armada-interface, a React web app, talks plain RPC/HTTP to Ethereum L1 and to armada-relayer, a conventional Express/Postgres server that indexes pool events with Ponder and charges a flat relay fee. No watcher-party federation, no bonded service-provider network, and no threshold-signed attestation substrate exist anywhere in the client, relayer, interface, or SDK repos.

Clients hold their own keys and funds today (`armada-interface`'s browser key manager); channels, once a client drives them, would be L1-collateralized and unilaterally exitable through the built adjudicator. The earlier plan's "only fixed infra is STUN/TURN plus a few emitters" claim does not describe today's deployment: `armada-relayer` is itself a conventional fixed server, not a thin bootstrap node.

The settlement rail — notes in, normal Nitro, notes out

Every flow resolves to one motion. Value leaves Armada's shielded pool as a note, funds a Nitro channel, and returns to a shielded note at the end. ArmadaNitroAdjudicator does the settling and holds the deposit/payout boundary in the same contract as the ForceMove dispute logic — there is no separate boundary contract. This is built: depositFromNote unshields a note into a channel, and a SHIELD-type allocation in _executeSingleAssetExit re-shields a channel's outcome.

No cross-chain swap is built. A multi-chain construction, with a shielded pool deployed on each chain and legs settling through mirrored channels, remains a draft (cross-chain swap design); it has no deployed custodian and no cross-chain adjudicator. Armada's one deployed hub custodian signs with FROST (see T2 below).

T0 · Ethereum anchor — settlement & shielded custody

Settlement is non-custodial Nitro state channels on Ethereum L1. Funds are locked in ArmadaNitroAdjudicator and allocated off-chain by co-signed state; a channel closes cooperatively at internet speed, or unilaterally via the ForceMove dispute game (challenge, checkpoint, conclude)[5]. If a party misbehaves, the user force-closes to their last co-signed state. The adjudicator only ever honors user-signed states, so a stalled counterparty can delay a user but cannot fabricate balances or move unsigned funds.

Built here: the shielded pool (PrivacyPool, T0.0), ArmadaNitroAdjudicator — a patched go-nitro adjudicator that also carries the deposit/payout boundary (T0.2) — and the governance/revenue contracts (ArmadaGovernor, ArmadaTreasuryGov, TreasurySteward, ArmadaToken, ArmadaCrowdfund, ArmadaWindDown, ArmadaRedemption). The circuits exist, with the Phase-2 trusted-setup ceremony still open (T0.1). Not built here: a venue/party registry and bond contract (T0.4), an on-chain sequencing-cert and fraud-proof verifier (T0.5), and a native channelized commitment for amount-privacy-in-play (T0.6). Full status on the item registry.

T1 · Ingestion — the proof path

The earlier plan called for a nimbus-eth1 state-diff emitter mapping into IPLD, served by watcher-ts. That pipeline is geth-only (plugeth), dormant since August 2024, and its current IPLD schema stores no receipt trie, so no proof connects a single log to receiptsRoot in it (labbook/2026-10-19-nimbus-verified-proxy-proofs.md). status-im/nimbus-eth1 instead ships a verified proxy — native, WASM, and a C/Go-bound library — that does the verification job upstream of the client: it anchors a header to a beacon light client, verifies storage with EIP-1186 proofs, and verifies a block's receipts by rebuilding the receipt trie against header.receiptsRoot. Rebuilding the trie proves both the inclusion of one log and the completeness of the block's logs at once, which an eth_getLogs range cannot do, since an omitted log inside a range is undetectable.

What is built: the proxy exists upstream, unintegrated. What is not: no Armada repo runs or embeds it; no server operates it against any Armada chain; armada-interface ships no WASM bundle; libverifproxy.a has no iOS or Android cross-compile target; and the proxy's genesis-parameter loader needs a fixturenet patch before it can verify armada-nitro's own test network (T1.2). See T1 ingestion for the full assessment.

T2 · Watcher substrate

The earlier plan called for a bonded federation of watcher parties serving proof-carrying feeds over watcher-ts, ts-nitro, @cerc-io/peer, and a threshold-signed attestation. None of that exists in any ship-armada repo.

With the nimbus verified proxy as the trust boundary (T1), a server-side watcher becomes optional: a cache a client may read from, then re-verify through the proxy. It is never itself a trust boundary. Today's live cache is armada-relayer's Ponder/Postgres indexer (relayer-v2/watcher), a conventional server out of the earlier plan, serving /v2/quick-sync over plain REST with no proof attached. armada-relayer's actor charges a flat USDC fee computed from a gas estimate, not go-nitro payment vouchers.

The one deployed threshold signature — FROST

armada-nitro's HubCustodian signs with FROST over secp256k1 (KECCAK-256), via the pinned frost-secp256k1-evm library. FROST secures one contract's hub-delegate signing, not a watcher federation's attestation; no federation, bond, or attestation substrate exists to apply it to.

T3 · Ordering & fault model (plan)

The earlier design calls for commit-reveal ordering so a venue cannot front-run or position-manipulate hidden orders, with threshold-signed inclusion receipts making censorship slashable. No sequencer, randomness beacon, data-availability layer, or attestation code exists in armada-poc or armada-nitro. This tier has no code and depends on T4 (a venue to order for) and T0.4/T0.5 (the bond and fraud-proof verifier), neither of which is built either. See T3 ordering.

T4 · Execution / venue (plan)

The plan calls for a posted-price RFQ venue in v1 — a single priceSetter wallet publishes bid/ask, take-it-or-leave-it, cleared over Nitro — with an automated market-making matcher as a later upgrade. No price-setter contract, no quote/settle ForceMove app, and no venue of any kind exists in armada-poc or armada-nitro. See T4 execution venue and Execution platform for the full plan.

T5 · Adapters

Armada's adapters are applications that move value in and out of the pool without touching the pool contract itself. Built: CCTP (cross-chain USDC, via PrivacyPool/PrivacyPoolClient/CCTPHookRouter) and Aave-v4 yield, through the pool's own adaptContract/adaptParams binding (ArmadaYieldAdapter.lendAndShield/redeemAndShield) — a bespoke Armada construction, not a Railgun RelayAdapt/Cookbook recipe; no RelayAdapt contract exists anywhere in armada-poc. For ETH yield, any non-blocklisted ERC-20 can already be shielded as a note, so a shielded wstETH note needs no new contract. Not built: a Swaps contract. See Yield & clearing.

Audit boundary. A future execution venue shared across multiple adapters would be a shared dependency with its own audit surface. This stays a plan consideration (T4), not a build decision, since no venue exists yet.

The CCTP adapter — cross-chain USDC on/off-ramp

"Privacy on Ethereum" describes where the shielded pool lives, not where the money is. Circle mints native USDC on around a dozen chains, so most users' USDC is not already on mainnet. The CCTP adapter is the cross-chain rail that fills and drains the pool, an adoption and liquidity adapter rather than a privacy primitive. CCTP is Circle's burn-and-mint protocol: burn on the source chain, mint native USDC on the destination against a Circle attestation, non-custodial, 1:1, with no slippage and no wrapped-asset or bridge-hack risk. This is built: PrivacyPool/PrivacyPoolClient/CCTPHookRouter implement cross-chain shield/unshield over CCTP v2.

CCTP is transport, not privacy. The burn shows sender and amount on the source chain and the mint shows recipient and amount on the destination; if the same public addresses appear on both ends the cross-chain link is trivial. Privacy comes entirely from binding the mint into the shield. Residual leaks: amount and timing correlation across the hop, and the mint transaction's origin, since no broadcaster/keeper submits it on the user's behalf today.

T6 · Client / apps

The earlier plan called for a fork of laconic-wallet, a React Native app, pairing with an in-browser or mobile Nitro node and a libp2p relay. armada-client, the repo meant to host that fork, has no application code: 45 files, all docs and config, no src/. The live client is armada-interface, a React 19 + Vite web app, independently written and wired to armada-sdk. It holds keys in browser memory (no BIP-39/HD custody, no secure enclave), scans and trial-decrypts notes locally, and runs a snarkjs Web Worker Groth16 prover in the browser. No native mobile prover exists. No code drives an armada-nitro channel lifecycle: no open/fund-from-note, propose/accept state, cooperative close, or force-close exists in armada-interface or armada-sdk. No client-side watchtower exists; only armada-nitro's e2e gate harness has one, for tests. armada-client docs/SPEC.md records the plan for a unified TypeScript stack on four targets — Linux server, browser, iOS, Android — with no shipped code yet. See T6 client apps.

Identity — an optional match filter

Identity stays optional and unbuilt. The design calls for a user to source a selective-disclosure attestation off-band — for example a Self zk-passport (nationality, age, OFAC-clear, personhood) — proven on-device and verified off-chain, anchored to an Ethereum address, with the shielded pool identity left unlinked. No such mechanism exists in the client today (T6.8). It would thread through no other tier if built, which is why it is called out separately rather than as a cross-cutting concept.

Cross-cutting · Privacy boundary

Privacy is delivered by funding and settling channels through Armada's own shielded pool: value is a commitment inside the pool, and it becomes visible only where it crosses into ArmadaNitroAdjudicator, at a deposit, a payout, or a force-close. There is no separate boundary adapter; the boundary is inside the adjudicator contract itself (see the settlement rail, above).

Caveats: identity privacy is only as strong as the pool's anonymity set, which grows only from deposits into Armada's own pool — there is no cross-pool proof and no onboarding bridge from another pool (ruling 5). Amounts are hidden inside the pool; the only leak is at the boundary amount, and a contested force-close reveals a channel's settled size on-chain. Hiding that too is the not-built T0.6 upgrade.

No Proofs of Innocence. No check stands between a user and the pool. Deposits, transfers, withdrawals and channel deposits proceed without any proof of origin, and none is planned (ruling 4). A user who must show where value came from uses the voluntary, off-chain selective disclosure protocol instead; it never gates pool use.
