Armada on Watcher Parties

A mobile-first, non-custodial, front-running-resistant private exchange — delivering Armada's services through bonded Laconic watcher parties, so the network runs on browser wallets and phones with almost no fixed infrastructure.

0. The shape of the network — mobile-first

The central requirement: every Armada service is delivered through watcher parties so that the overwhelming majority of the network is browser wallets and mobile apps talking peer-to-peer. The only fixed infrastructure is (a) a handful of STUN/TURN servers for NAT traversal between phones/browsers, and (b) a small number of plugeth-based Ethereum state injectors that feed L1 state into the watcher parties. Everything else — sync, metering, matching, settlement, threshold attestation — is run by the bonded service-provider federations themselves and by the clients.

Clients hold their own keys and funds (channels are L1-collateralized); a watcher party never takes custody and can be exited unilaterally. The two boxes of fixed infra are deliberately small and stateless-ish — STUN/TURN carry no trust, and plugeth injectors only publish verifiable state.

1. ex_net — the design ancestor

Vulcanize's 2017 ex_net whitepaper[1] already specified this system: a bonded, federated venue for the privacy-preserving, trust-minimized exchange of crypto-assets across chains, where assets never leave the trader's custody (they sit in parent-chain payment channels) and the federation only matches, prices, and authorizes settlement. It gave us the vocabulary we still use — traders, liquidity providers, validators; bonding; per-block auditable snapshots; liquidity proofs (signed attestations that assets are available to trade for a bounded time); tunable privacy; and the observation that a truly "decentralized" exchange as a noun cannot prevent operator front-running, so you instead run a bonded federation you can punish.

What has changed since 2017: we no longer need a bespoke Tendermint chain to be the fair-ordering and settlement layer. Nitro state channels provide non-custodial settlement on Ethereum L1, and a watcher party provides fair ordering and attestation — so ex_net's goals are realized as three decoupled layers instead of one monolithic chain. The ex_net "identity proofs" and "address signing" sections[1] are the direct ancestor of the identity model in §5.

2. Watcher parties — the venue substrate

A watcher party is a bonded federation of service providers that collectively serves one data need — the exact "Federated Cache" role in Laconic's designed Service-Provider Marketplace. In this design a watcher party is also the exchange venue: it delivers all Armada services at once.

ServiceDelivered by the watcher party as…
Private shielded-pool syncfederated cache serving proof-carrying, everyone-gets-the-same-bytes note streams (clients scan locally & privately)
Metering / paymentsper-request Nitro vouchers (§3)
Matching / venuecommit-reveal sequencing + a plaintext matcher over revealed orders (§7)
Attestationthreshold-Schnorr (DSS) inclusion receipts, sequencing certs, liquidity-proof snapshots (§4)
Membership / bondingan on-L1 registry + bond; disputes and slashing settle on L1 (§3)

The client is the Laconic wallet — a React Native app that runs on Android and iOS[21] (with a browser build[22]): it custodies keys and signs both Cosmos and EIP-155 requests over WalletConnect, and pairs with an in-browser / mobile Nitro node for payments and a libp2p relay. This is the mobile-first shape the MobyMask stack[3] already proved end-to-end (app-specific signing + in-browser Nitro + p2p relay to a keeper). The watcher framework is watcher-ts[2]; the TypeScript Nitro port that runs a node inside the browser is ts-nitro[4]. The plan requires updates to the wallet — notably returning the signer public key on cosmos_signAmino and wiring commit-reveal + settlement receipts.

Why "party," not "chain": the federation only needs to (a) agree on which commitments are in an epoch and (b) fix an order — a sequencing-and-attestation task, not replicated global execution. That is a far weaker (and cheaper) primitive than BFT consensus, and it is what lets the network live on phones.

3. Nitro — settlement & custody

Settlement is non-custodial Nitro state channels on Ethereum L1. Funds are locked in the NitroAdjudicator / MultiAssetHolder and allocated off-chain by co-signed state; a channel is closed cooperatively at internet speed, or unilaterally via the ForceMove dispute game — challenge, checkpoint, conclude[5]. This is the escape hatch that makes the venue safe: if a party misbehaves, the user force-closes to their last co-signed state for a refund; no settlement receipt ⇒ force-close returns the pre-fill deposit. The adjudicator only ever honors user-signed states, so a byzantine federation can stall you but cannot fabricate balances or take unsigned funds.

    struct AppData { bytes32 h; bytes preImage; }   // reveal preimage of h to unlock

}

Beyond the hashlock example, go-nitro ships a full multi-asset swap protocol (Deepstack, 2024): protocols/swap (NewObjective, IsValidSwap, AcceptSwap)[6], the SwapChannel type[7], and the demo demo/swaps.md. Metering uses payment vouchers[8] over virtual channels[9]. Cross-chain / L1↔L2 movement reuses the Bridge mirrored-channel construction[10]. laconicd already embeds go-nitro as a Cosmos server — server/nitro wires the L1 chain service and adjudicator addresses[11] — so the pattern of "a node that speaks Nitro against Ethereum" is proven.

4. Schnorr DSS — the federation signature

The watcher party signs everything it attests to — inclusion receipts, epoch sequencing certificates, liquidity-proof snapshots — with a threshold Schnorr signature. This is the chain-signatures library: Ethereum-compatible Schnorr (ethschnorr.Sign / Verify)[12] and the Distributed Schnorr Signature protocol — Stinson & Strobl (t, n) — in ethdss (NewDSS, Signature, Verify)[13], built on a kyber DKG.

Two properties matter for the exchange:

  • On-chain verifiable. Because it is Ethereum-flavoured Schnorr, an L1 contract can verify a party's aggregate signature — so a sequencing cert or a censored-commit receipt becomes a slashable fraud proof against the party's bond.
  • Threshold direction is safety-first. A t-of-n threshold tolerates t−1 malicious for safety and n−t offline for liveness. We choose t high (e.g. 4-of-7) so forging an attestation requires a large coalition; liveness failure degrades to halt, not loss because settlement is non-custodial. (This is why a BFT-style small quorum like 3-of-11 would be wrong here — it would let any 3 members forge.)
Note: the threshold key is used for signing only. We do not run a threshold-encrypted mempool — with the sequencer and the key-holder being the same federation, encryption gives no real fairness (a colluding threshold can decrypt-then-order). Fair ordering is achieved with commit-reveal instead (§7).

5. Identity — ex_net proofs + the Laconic Matchmaker

The identity layer is described entirely by two existing pieces of Laconic work; it is deliberately thin and privacy-first.

ex_net identity proofs

ex_net[1] already defines the primitive: a user links an external key to their trading identity by signing a message with the external private key that embeds their venue public key, and — in its forward-looking form — can prove a match (e.g. passport ↔ liveness) and record only the proof, never the underlying data. Identity is therefore an optional, user-initiated, selectively-disclosed proof that sits beside the shielded default; the venue stays identity-blind unless a counterparty or jurisdiction requires a proof. The shipped precedent is laconicd's onboarding module, whose on-chain Participant record carries role and kyc_id, and whose EthPayload is exactly the "sign with the external key to bind identities" pattern[14].

The Laconic Matchmaker

The Laconic Matchmaking Services proposal[15] supplies the compliance-gating half: a privacy-preserving matchmaking service that pairs technically-qualified operators with capital backers "in a way that's compliant with international broker-dealer laws and respects their users' privacy," implemented as encrypted computation that matches number ranges and finds intersections of number intervals. In exchange terms: the matcher can verify that two parties satisfy each other's constraints (jurisdiction, accreditation, size band, KYC status) without either party — or the venue — learning the other's identity or exact values.

Together these cover the requirement: identity is private from the venue by default (§8), and any required attribute (compliance, qualification) is established by an ex_net-style selective proof or by encrypted matchmaking — not by revealing who you are. The underlying FHE / encrypted-computation machinery is a useful implementation detail, but the design only depends on the two abstractions above.

6. Ethereum state injection (plugeth)

The second and last piece of fixed infrastructure is the mechanism that gets L1 state into the watcher parties: Vulcanize's plugeth[16] + plugeth-statediff[17], which extract full Ethereum state diffs from a geth node without forking geth, and the IPLD services that index and serve it — ipld-eth-server[18] and ipld-eth-state-snapshot[19].

This is what makes private sync possible: a watcher party ingests the Railgun shielded-pool commitments/nullifiers and the Nitro adjudicator events via plugeth, then serves proof-carrying, identical-for-everyone note streams metered by Nitro. Clients scan those streams locally, so no RPC provider ever fingerprints a user against the pool — the single property Armada's anonymity set depends on. A few injectors serve the whole network; the phones and browsers do the rest.

7. Ordering, latency & fault model

Fair ordering = commit-reveal

Orders are hidden from the venue during ordering with commit-reveal, not client-side ZK: a phone generating a SNARK per order costs seconds, whereas a reveal round-trip is tens of milliseconds, and the user is already interactive through settlement. Flow: commit = H(order ‖ salt) → the party seals the epoch and emits threshold-signed inclusion receipts (so censorship is slashable) → a post-seal randomness beacon fixes positions → the user reveals → the matcher runs over revealed orders in the fixed order. The party cannot content-front-run (it only saw hashes) or position-manipulate (the beacon is post-seal). ZK order submission remains an opt-in for offline submitters or server-side provers.

Latency & receipts

A cooperative fill is 3 RTT + Δ (commit, reveal, settle) with Δ ≈ the party's co-located sealing window (single-digit ms). Settlement is one round trip whose two legs are both mandatory: the user signs first, the venue returns a bond-enforced settlement receipt. There is no fire-and-forget — every fill terminates in either a co-signed receipt or a slashable proof of its absence.

Griefing is a non-issue here

Because the venue is the one providing asks, a user who withholds a reveal harms no third party — the ask is a standing quote available to all, so a non-revealed commit blocks no other user's liquidity. Modeled turn-by-turn, the only theoretical residual is a sub-second free option on a stale quote, worth ~nothing as long as the reveal timeout ≤ the quote-repricing interval (a knob the venue controls). So anti-griefing collapses to a nominal anti-spam commit fee.

Failure = halt, not loss

If the party stalls or goes below its liveness threshold, users force-close to their last signed state and are made whole; a watchtower guarantees the latest state even for an offline user. Non-custody means a dead party freezes trading, never funds.

8. Privacy boundary (Design A)

Privacy is delivered by funding and settling channels through a Railgun-style shielded pool via an adapter[20] — the same adapter pattern Armada already uses for CCTP/Aave/swaps, with a Nitro adapter added. The venue's visibility begins at the shield boundary and never reaches behind it: it sees the shielded-side order terms it must match and an ephemeral channel identity, but not who you are, where the funds came from, your on-chain history, or that two trades were the same person. The venue is a blind, non-custodial matcher.

Caveats: identity privacy is only as strong as the Railgun anonymity set and is subject to amount/timing correlation (mitigate with denominations/batching and a fresh per-channel identity). The only thing still visible to the venue is the trade's amounts/terms — hiding those too is Design B (ZK matching + a "shielded ForceMove" dispute over hidden state), which is out of scope for v1.

Namada is not Design B. Namada's MASP is an excellent multi-asset shielded-note primitive, but Namada is an L1 with global consensus — not a state channel — so it has no off-chain, non-custodial, unilateral exit and runs at chain speed. It attains privacy the way ex_net attained fairness: with a chain. MASP-the-circuit could serve as a note primitive for a future Design B; Namada-the-chain does not provide the channel-speed exit this design requires.

10. Net-new work

  • Epoch set-agreement for the watcher party (leader-proposes + threshold-attest + receipt-backed censorship fraud proofs) — deliberately not BFT.
  • On-chain verifier + fraud-proof game for the sequencing certificate and inclusion receipts, tied to the party's L1 bond (uses chain-signatures verification).
  • Nitro ↔ Railgun adapter (boundary shielding: note-funded, note-settled channels).
  • Commit-reveal + post-seal beacon integration into the matcher, plus a watchtower.
  • Multi-asset outcomes for the Nitro integration (today single-asset), if fills span assets.

Deferred (Design B): ZK matching + shielded ForceMove, to hide trade amounts from the venue itself; native BTC settlement beyond an HTLC leg.
