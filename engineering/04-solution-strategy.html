4. Solution Strategy

This section records the fundamental decisions that shape the system and the order in which they ship. Every claim grounds in the §5 registry (for item ids) and the §9 ADRs (for rationale); the supporting detail lives in the T#.# tier docs, and the risk detail lives in §11.

4.1 Core strategy — nitro-on-railgun

The core idea is one sentence (ADR-0004):

notes in → normal Nitro → notes out.

A shielded note is unshielded into ArmadaNitroAdjudicator's depositFromNote, which funds a Nitro channel. Parties then play arbitrary off-chain ForceMove games, and a SHIELD-type allocation pays the channel outcome back out into fresh notes. The code merges this deposit/payout boundary into the adjudicator itself (ruling 1, labbook/2026-10-19-docs-versus-code.md; T0.2 in §5). The Nitro game analysis and the Railgun privacy analysis stay fully isolated; they meet only inside depositFromNote and the SHIELD payout path. This buys optimistic exits and arbitrary settlement games over shielded value with no new cryptography. Armada's adapters do not use Railgun's RelayAdapt/Cookbook recipe pattern anywhere; the Aave-v4 yield adapter instead calls the pool's own adaptContract/adaptParams binding (T5.0b, ArmadaYieldAdapter.sol:27-40).

This is integration, not new cryptography, with one caveat. The thesis holds for the settlement rail (T0.2's merged adjudicator + T6.x), which is reuse plus a patched go-nitro: six commits change the vendored src/nitro contracts (EIP-1271 participants, a guarantee-check fix, measured-balance deposit crediting, an asset allow-list, a reentrancy lock, SafeERC20 payout), so this is a patched adjudicator, not a vanilla deploy (armada-nitro@55939ef:src/ArmadaNitroAdjudicator.sol). It does not hold for the shielded pool (T0.0) and its circuits (T0.1): those are Armada's own pool and circuits, its own implementation of the Railgun design, spec-compatible, and therefore audit-critical crypto-engineering (of a well-understood, de-risked design, not novel cryptography). The hard cryptographic assets break down as:

  • T0.0 / T0.1 — the shielded pool and its circuits, Armada's own implementation of the Railgun design (ADR-0014), with the pool already deployed and the circuits' Phase-2 ceremony still open (v1.0.0-ceremony manifest, every shape "status": "open", no beacon). Amounts are hidden in-circuit; the SNARK enforces value-conservation and range, so $50 and $5M are equally opaque — no Tornado-style denomination buckets.
  • T0.2 — ArmadaNitroAdjudicator, a patched go-nitro NitroAdjudicator / ForceMove / MultiAssetHolder, deployed and carrying the deposit/payout role too (see above).

Against that, the remaining v1 surface is enumerable:

The only novel cryptography anywhere in the plan is T0.6 (native channelized commitment, "fork-lite"). It is not built and, if greenlit, re-runs the Phase-2 ceremony over Armada's own circuits (ADR-0003). v1 needs no novel cryptography and no new consensus/ordering (ADR-0007) — the pool and circuits (T0.0/T0.1) reimplement a known design rather than invent one — and because a posted price has nothing to front-run, the fair-ordering stack (T3) stays a plan.

Walking skeleton — the first integration target

Before hardening any single tier, stand up one thin end-to-end slice on a fixturenet that exercises every boundary at least once:

shield → depositFromNote → trivial ForceMove settle → SHIELD payout → scan
  T0.0        T0.2                T0.2 / T4.1 stub         T0.2        T6.1

Concretely, the slice shields a known value into the pool (T0.0), then unshields-in through depositFromNote to fund a Nitro channel (T0.2). It drives a trivial ForceMove app — a single co-signed fill, standing in for the real T4.1 quote/settle — to a finalized outcome, pays that outcome back out into fresh notes via the SHIELD payout (T0.2), and scans and confirms balances on-device against the nimbus verified proxy (T6.1 over a T1.0/T1.1 proof, once integrated). This exercises the notes-in-Nitro-notes-out thesis end-to-end with the smallest possible game.

The sequence, at a high level

The full stage-by-stage sequence, with chunks, points and 5090 hours, is build-plan.md. At a high level:

  • Already done. T0.0, T0.1 (pool and circuits, Phase-2 ceremony pending), T0.2 (adjudicator with the merged deposit/payout boundary), the CCTP and Aave-v4 adapters, the v1 governance/revenue contracts, the FROST hub custodian core, and the web wallet. Nothing later needed to wait for these; they already exist.
  • Next. Two independent tracks run first: the armada-client daemon (Phase 1) and the proof path (patch the fixturenet genesis, operate the nimbus verified proxy, run the first proof). Both unblock the most later work — client reads and every later client phase depend on them.
  • Then, in parallel. A non-upgradeable, contract-owned-notes pool deploy and a generic ZK IForceMoveApp for hidden-balance channels (209-point list families F1 and F2). Both feed a Baal treasury governance migration and the armada-nitro side of contract-owned collateral (F3 and F4), which in turn feed client support for the new artifacts (F5) and the armada-client channel/ watchtower phase (Phase 2).
  • Later. Mobile (armada-client Phase 3), the watcher federation, the production Phase-2 ceremony, venue v1, the v2/deferred backlog, and the Sepolia-then-mainnet cutover, in that rough order — everything proven on the fixturenet before Sepolia, and on Sepolia before mainnet.

The walking skeleton above is the first integration target inside this sequence, not a separate track: it becomes concrete once the proof path (next) and the contract-owned-notes pool (then) exist.
