Shielded games over Nitro — structure

standalone walkthrough · 2026-09-24

What this shows

Armada holds value as shielded notes in its pool: sender, recipient, and amount are hidden in-circuit. This page shows how a user takes part of a note, opens a Nitro state channel to a hub, and plays games against the hub or other users, with every game enforceable on Ethereum and every exit landing back in the pool at unused addresses.

A game is a ForceMove application: a contract published on Ethereum that defines which state transitions are valid and how a finished game splits its stakes. Players exchange signed states off-chain. Ethereum sees a game only if a player refuses to follow its rules.

Status. This page is a plan. No published game contracts or hub channel-opening code exist yet. The deposit/payout boundary it diagrams as a separate contract is built inside the Nitro adjudicator (ArmadaNitroAdjudicator, depositFromNote and its SHIELD payout path, T0.2).

The structure in four steps:

  1. Shield. A user shields any asset into Armada as normal and receives a note.
  2. Open a channel to a hub. Using a fresh address and a relayer, the user takes a split of that note and opens a Nitro channel to a hub. The hub is a liquidity provider whose identity is private. It can deny service but cannot steal: every balance is enforceable on-chain without its cooperation.
  3. Play games. The user plays any published game with the hub, or with other users routed through the hub. A player who breaks a game's rules loses on Ethereum under that game's rules. Games that end cooperatively net back into the hub channel off-chain, and funds are shielded into Armada at otherwise unused addresses when the user exits.
  4. First games: Aave USDC yield, and swapping shielded WETH for wstETH.

  1. Shield. An ordinary Armada shield. The user holds a note.
  2. Fund the hub channel. The user signs an unshield of part of the note and hands it to a relayer, which submits it from its own address and is paid from the shielded balance. The pool spends the note, returns the change to a new user note, and sends the split as ERC-20 to the deposit/payout contract (T0.3), which escrows it into the User–Hub channel on the Nitro adjudicator. The split amount is public; the owner is not.
  3. Play. Each game runs off-chain against a game contract published on Ethereum. The counterparty is the hub or another user routed through the hub over a virtual channel. When a game ends cooperatively, its outcome nets into the hub channel with no chain event, so many games cost one channel open.
  4. Exit. A cooperative close settles the hub channel, and T0.3 shields the user's balance into fresh, unused addresses.

When a player breaks the rules

A game is enforced on Ethereum by the same adjudicator that holds the channel. The honest player puts the latest co-signed game state on-chain. If the other player does not answer with a valid later state before the challenge window closes, the game finalizes under its own rules. A player who stalls or cheats therefore loses by those rules, and the loss is bounded by that game's stakes.

Adjudication reveals the stakes of the disputed game, not the user's balance in the pool. The hub-channel deposit is different. It is public from the moment the channel opens, as the split amount of the funding unshield (Design A, ADR-0005). A dispute against an uncooperative hub also forces the hub channel on-chain, because Nitro releases a game's guarantee only from a finalized hub channel (reclaim in go-nitro's MultiAssetHolder). None of these amounts is linked to the user's identity. Hiding the amounts themselves is the T0.6 fork-lite upgrade (A.9).

The first games

Swapping shielded WETH for wstETH. The hub quotes a price. The user signs one channel state that moves the agreed WETH to the hub and the agreed wstETH to the user. The hub countersigns. Both assets live in the channel's escrow, so the swap is atomic: ForceMove accepts or rejects whole states.

Aave USDC yield. The hub holds the Aave position and provides liquidity. The user swaps USDC for Aave's non-rebasing share token waUSDC inside the channel, by the same co-signed reallocation. Interest accrues to the holder of waUSDC, so no rate reference reaches the chain. The Aave interaction is the hub's own public activity and is not linked to the user.

How the first games are built. ADR-0017: no app per game. Each game is one co-signed reallocation of a multi-asset channel state under ConsensusApp. Invariants and contract requirements: 15.

Games with hidden state

A second kind of game keeps its state hidden even in a dispute. ZkForceMoveApp (armada-nitro src/apps/) accepts a channel state only when the state carries a valid Groth16 proof, checked by the pool's Snark library against a verifying key fixed at deployment. LedgerForceMoveApp builds on it: each state commits to the parties' balances, and each move proves that the new balances keep the old total without revealing either balance (circuit Ledger, armada-circuits src/operations/Ledger.circom). It also requires each state's previous commitment to equal the next commitment of the state before it. BattleshipForceMoveApp uses the same base for a game whose board stays hidden: the defender proves each hit or miss against its own committed board.

Two parties per ledger. The ledger is two-party, which matches the hub topology: every user's channel is with a hub, and user-to-user play runs over virtual channels built from those two-party channels. A ledger commitment hashes every party's balance and one salt with one circomlib Poseidon(n). circomlib 2.0.5 defines Poseidon for state widths up to 17 (poseidon.circom), that is at most 16 inputs, so a single-hash commitment covers at most 15 parties. A ledger for more parties needs a tree of Poseidon hashes, which adds constraints to every move. Multi-party ledgers are out of scope.
