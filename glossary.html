Glossary

Terms span three worlds — Vulcanize/Laconic/cerc-io (the substrate), Nitro (state channels), and Railgun/Armada (the shielded pool) — plus this project's own design terms. Several words collide; the collisions are resolved first.

1. Word collisions (read this first)

"Relay" — two unrelated things

TermWhat it isRole
Relay (Laconic / libp2p)a libp2p transport relay: routes p2p messages and does NAT traversal between browsers/phones and keepers. Pure network plumbing; no trust, no on-chain role.network transport
Relay (Railgun / Armada)a Broadcaster (formerly "Relayer"): submits a user's encrypted, ZK transaction on-chain and pays gas, so the public origin is the broadcaster's address, not the user's. Talks to users over Waku.on-chain write

Resolution: the Railgun relay's Laconic analog is the keeper (tx submitter), not the Laconic relay. Unqualified "relay" here = the libp2p transport relay.

"Watcher" vs "Watchtower" vs "Keeper"

TermWhat it does
Watcher (Laconic)proof-carrying, metered state indexer: ingests chain state (nimbus-eth1 state-diff emitter → IPLD) and serves verifiable query results / note-streams. Read-and-serve.
Watchtower (state channel)watches L1 for a stale-state challenge and responds with your latest signed state (checkpoint/respond) so an offline user isn't defrauded. = a watcher (read) + a bonded responder (write).
Keeperthe node that submits transactions on-chain on the user's behalf (MobyMask lineage). The Laconic analog of a Railgun Broadcaster.

Duality: the watcher protects the read side of pool privacy (no RPC fingerprints you scanning the pool); the keeper/broadcaster protects the write side (no EOA links you submitting). Same anonymity set, opposite ends.

"Layer" vs "Tier"

  • Tier (T0–T6) — this project's stack rungs, in the software-architecture (n-tier) sense. See §5.
  • Layer 1 / Layer 2 (Ethereum) — blockchains. We write "Ethereum L1" only where we mean the chain.
  • Execution / settlement / DA layers — modular-blockchain vocabulary; deliberately not used to name our tiers (hence "tier").

"Swap"

  • swap (Nitro protocols/swap) — go-nitro's multi-asset off-chain swap protocol / SwapChannel (settlement primitive).
  • Swaps (Armada adapter) — the user-facing "swap shielded A→B" adapter; an application on the execution platform.
  • matcher swap — a fill from the ex_net matcher, settled via the Nitro swap primitive.

"Adapter"

  • Adapter (Armada) — a governance-added module in Armada's Adapters tier (CCTP, Aave-v4 yield, Swaps).
  • Nitro↔Railgun adapter — a net-new boundary contract funding/settling Nitro channels from Railgun notes (Design A privacy boundary).
  • IForceMoveApp — a Nitro app-logic interface (e.g. HashLockedSwap); "adapter" in the Nitro sense.

"Validator"

  • Validator (ex_net) — a bonded federation member that matches/prices/authorizes settlement. ≈ today's watcher-party member.
  • Validator (Cosmos / laconicd) — a PoA consensus validator on the laconicd chain. Unrelated to the exchange venue.

"Proof" (distinct artifacts)

  • Liquidity proof — signed attestation that assets are available to trade for a bounded time (ex_net).
  • Inclusion receipt — threshold-signed proof an order-commit was included in an epoch (censorship becomes slashable).
  • Sequencing certificate — threshold-signed proof of an epoch's fixed order.
  • Fraud proof — on-chain evidence of misbehavior, slashable against a bond.
  • ZK proof / zk-SNARK — Railgun's Groth16/BN254 proof of a valid shielded transaction.

"Pool"

  • Shielded pool — Railgun's privacy pool (one shared anonymity set). Armada's core.
  • LP pool / vault — market-making capital in the execution platform. Unrelated to the shielded pool.

3. Nitro / state-channel terms

  • State channel — off-chain, co-signed balance updates collateralized on L1; closed cooperatively at internet speed or unilaterally via dispute.
  • NitroAdjudicator — the L1 contract holding funds and adjudicating outcomes.
  • ForceMove — the dispute game: challenge → checkpoint → conclude. Only ever honors user-signed states.
  • MultiAssetHolder — holds multiple assets per channel.
  • Virtual channel (virtualfund) — a channel routed through a hub without a new on-chain deposit.
  • Voucher — a signed pay-per-request micropayment over a (virtual) channel; the metering primitive.
  • Force-close — unilateral exit to your last co-signed state (safety escape hatch: failure = halt, not loss).
  • HashLockedSwap — an IForceMoveApp example: reveal a preimage to unlock (HTLC-style).
  • SwapChannel — go-nitro's channel type for the swap protocol.
  • Bridge.sol — mirrored L1↔L2 channel construction (cross-chain movement).
  • Watchtower — see §1.

4. Railgun / Armada terms

  • Railgun — Ethereum privacy protocol: a shielded pool using zk-SNARK circuits (BN254 / Groth16). Immutable core.
  • Armada — pluggable asset-privacy infrastructure for USDC on Railgun; three tiers (shielded pool / adapters / apps+SDK), crowdfunded, ARM-token DAO + steward. @ship_armada, armada.wtf. In testnet.
  • Shielded pool — the shared privacy pool; privacy compounds with volume (one anonymity set).
  • Note — a shielded UTXO-like value commitment inside the pool.
  • Commitment / Nullifier — the note's on-chain hash / its spend-marker (prevents double-spend without revealing which note).
  • 0zk address — a Railgun private receiving address.
  • Broadcaster / Relayer — see §1 ("Relay", Railgun).
  • Waku — decentralized p2p messaging protocol (libp2p-based) for broadcaster↔user comms; light-client friendly (filter / lightpush / store).
  • CCTP — Circle's Cross-Chain Transfer Protocol (burn-and-mint native USDC); Armada's cross-chain adapter, used as mint-and-shield.
  • Aave-yield adapter — USDC shielded yield via an LP-buffered, batched Aave rail (no per-user public deposit); ETH yield instead uses a shielded wstETH note. Armada's adapter tier.
  • MASP — Namada's Multi-Asset Shielded Pool primitive (a note primitive; not a state channel — see the Architecture Design-B note).
  • RelayAdapt / recipe — Railgun's cross-contract module: an atomic unshield → external call → reshield (Cookbook "recipes", e.g. an Aave deposit). The value-moving "adapter" — not a custodial vault, not DSS.
  • wstETH / weETH — non-rebasing LSTs (value via a rising exchange rate). Held as a shielded note they earn ETH staking yield intrinsically — no Aave/LP needed.

5. This project's design terms

  • Tier (T0–T6) — the stack: T0 Ethereum anchor · T1 ingestion · T2 watcher-party substrate · T3 ordering · T4 execution platform (ex_net) · T5 adapters · T6 client/apps. Software-architecture tiers — not blockchain layers.
  • Watcher party — a bonded federation of service providers serving one data need; here also the execution venue. A sequencing-and-attestation role, not a BFT chain.
  • Commit-reveal — fair ordering: commit = H(order‖salt) → seal epoch + inclusion receipts → post-seal beacon fixes positions → reveal → matcher runs. Blocks operator front-running without client-side ZK.
  • Post-seal randomness beacon — randomness revealed after the epoch is sealed, fixing order positions.
  • Epoch set-agreement — the watcher party agreeing which commits are in an epoch and their order (leader-propose + threshold-attest + censorship fraud proofs). The core net-new, highest-risk piece.
  • Data availability (DA) — publishing the revealed epoch so anyone can recompute/challenge.
  • Frequent batch auction (FBA) — discrete per-block clearing at a uniform price, allocation pro-rata + lottery; defeats latency/HFT front-running (Budish–Cramton–Shim 2015).
  • Curve order — an order specifying price-varying liquidity over a range (vs a point), flattened into fillable chunks. (Predates Uniswap v3 concentrated liquidity.)
  • Filler-filtered order — an order carrying an allowlist of who may fill it; empty ⇒ open (lit/CLOB), non-empty ⇒ private/RFQ.
  • CLOB / RFQ — Central Limit Order Book (public, lit) / Request-for-Quote (bilateral, private). The matcher unifies both in one order type.
  • LP vault — pooled market-making capital run by a keeper (lets passive LPs participate).
  • Threshold Schnorr / DKG / t-of-n — the federation signature (via chain-signatures); we pick t high (e.g. 4-of-7) so liveness failure = halt, not loss.
  • Design A / Design B — A (this project): boundary privacy via a Railgun-style shielded pool + adapter; the venue is a blind matcher but sees trade amounts/terms. B (deferred): ZK matching + "shielded ForceMove" to hide amounts/terms from the venue itself.
  • Posted-price venue (v1) — a single priceSetter (one L1 wallet → governance) posts bid/ask on both sides; take-it-or-leave-it; cleared over Nitro. No order book, no price discovery — nothing to front-run. Discovery is the v2 matcher.
  • Taker / maker (LP) — taker: swaps notes privately at the posted price, capacity-bounded, fully private. maker/LP: provides inventory, holds a public aggregate position, earns the spread — voluntary + compensated. Saturating takers are offered the maker role, never forced to a public deposit.
  • v1 / v2 / v3 — scope split: v1 = Armada support (posted price + clearing + private sync + mobile client + CCTP + boundary + base yield); v2 = ex_net matcher (price discovery + fair-ordering); v3 = Design B. See Build plan · versions.
