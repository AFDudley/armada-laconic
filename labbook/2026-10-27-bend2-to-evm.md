## Bend2 to verified EVM bytecode: a research report

date: 2026-10-27 · read-only research, no repository file changed except this one

### (a) The answer

An EVM emitter for Bend2 already exists, but it is not part of Bend2 and it does not reach verified bytecode. The missing piece is not an emitter; it is a proof that connects Bend2's own proof system to the EVM semantics EquiVM and Armada already trust (EVMLean, checked in Lean). The coordinator's position holds: an emitter alone gives bytecode with no proof, and the shortest route is not "export Bend2 to Lean," because BendTT (Bend2's kernel) and Stele (EquiVM's specification language) are two independently designed formal systems with no bridge between them today, and a past session found the adjacent, smaller problem (lifting a Lean tactic proof into BendTT) to be "a research project in its own right" (session `01a162aa-6ca3-71fc-be3b-03460bb00208`, 2026-10-25). The route that needs the least new machinery is to treat Bend2 the way EquiVM already treats Solidity and Vyper: write or draft a Stele specification and run EquiVM's existing per-contract refinement proof against the compiled bytecode, using the third-party Bend2 EVM backend only as a drafting aid and a differential-test oracle, not as part of the trust chain. For Armada specifically this route does not remove the one proof the build plan already names as missing and unscoped: the Lean-to-Stele symbolic-to-concrete refinement (`engineering/build-plan.md:124`, "No existing tool provides this proof").

### (b) What Bend2 has today, toward EVM and toward Lean

**Toward EVM: nothing in Bend2 itself; a third-party backend exists outside the project.**

- Bend2's own compiler emits two targets only: C (host, CUDA and Metal from one C source) and JavaScript. `AGENTS.md` in the Bend repo: "`bend2/comp.ts` is the one compiler: the C runtime (host and device from one source), the C emitter and the JS emitter." No EVM, Solidity, Yul or WASM path exists in `bend2/comp.ts`; a direct grep of the file for `EVM|Solidity|Yul|bytecode` found no matches, and `bend2/bendtt.lean` (3,981 lines, read in full — see below) has none either.
- Upstream `bendlang/bend` has no issue or search hit for EVM, Ethereum, blockchain, Solidity or smart contracts (`gh issue list --repo bendlang/bend --search "..."`, run 2026-10-27). The closest hits are a planned WASM library target for the browser (issue #1352, open) and a closed request for built-in cryptographic hash functions (#368, closed as out of scope). A third target, Python, was built by a fork (`AFDudley/bend` branch `python-target`) and proposed upstream as issue #1827 ("Python target: a first pass"), still open and not merged because the compiler file exceeds the repo's permanent token cap (session `01a162aa-6ca3-71fc-be3b-03460bb00208`, message `5aea8f26`, 2026-10-22). No EVM-equivalent issue exists.
- A real EVM backend for Bend2 exists, built by a third party: [`ind-igo/bend-evm`](https://github.com/ind-igo/bend-evm), "EVM backend for Bend 2, written in Bend," consuming a checked `Core.Program` from a separate frontend fork, [`ind-igo/bend-frontend`](https://github.com/ind-igo/bend-frontend). Its pipeline: `contract.bend → Frontend.check → read → IR → lower → Yul → solc → bytecode`, with two parts proved in Bend2's own kernel (BendTT) and two parts only tested:
  - **Proved** (checked by `bend --verdict`, i.e. by `bendtt.lean`'s kernel): the certificate that the IR equals the source contract function, and the law that `lower` (IR → the project's own modeled Yul fragment) preserves every IR command's outcome, for every environment, continuation and state (`ind-igo/bend-evm` README, "Certificates" and "Lowering" sections).
  - **Tested, not proved** (README, "Lowering" section, verbatim): "the printer, the dispatcher and ABI decoding, the mapping layout, the parameter types in the signatures of events, errors and calls... `solc`, and the match between the Yul model and the EVM on words below 2^256." Confirmed by differential tests against `anvil` and against Solidity references, not by a checked proof.
  - The project's own roadmap states the boundary directly: "Three proof layers check in Bend... The README states the boundary: the lowering is proved; the dispatcher, ABI encoding, printer, `solc`, and the match between the Yul model and the EVM are tested." (`ind-igo/bend-evm/ROADMAP.md`, milestone M1).
  - Feature coverage as of the milestones read (M1–M27 done; M28 loops, M29 contract creation, M30 `delegatecall` and low-level calls not done): checked arithmetic, mappings and nested mappings, events, custom errors, view and write external calls with callback modeling, reentrancy proofs, transient storage, multi-word returns, and `bytes`/`string` parameters. It has no symbolic (Dolev-Yao style) hash model; its Keccak is concrete and assumed collision-free, same as Solidity's own assumption (README, "Model" section).
  - The frontend's own guidance names the exact gap: "In that example, the theorem covers IR → the modeled Yul fragment... The connection to the printed Yul and the actual EVM is tested, not formally proved." (`ind-igo/bend-frontend/docs/backends.md`, "The current boundary").

**Toward Lean: a formally verified kernel, built and consistency-proved in Lean, with no connection to any other Lean project.**

- `bend2/bendtt.lean` (read in full, 3,981 lines) is BendTT: Bend2's own dependent affine type theory, implemented and proved consistent as a standalone Lean 4 program. It is organized in three parts, by its own section markers:
  - **THEORY** (lines 1–1483): the `Term` syntax (`bendtt.lean:74-94`: `Var, Ref, Ann, Let, Typ, Min, All, Lam, App, Sig, Tup, Prj, Enu, Lab, Mat, Efq, Eql, Rfl, Rwt`), substitution and renaming, a bidirectional type checker (`Term.check`/`Term.infer`, around `bendtt.lean:1099-1239`), a termination ("live") checker that decides structural descent on recursive calls (`bendtt.lean:1241-1443`), a `.bendtt` text parser, and a CLI `main` (`bendtt.lean:1469-1482`) that prints `ALL PROOFS CHECK` or `SOME PROOFS FAIL`.
  - **CLAIMS** (lines 1484–1739): the declarative theory the checker is proved sound against — parallel reduction `Par`/`Pars`, conversion `Conv`, subsumption `Fits`, typing `Typed` (`bendtt.lean:1510-1603`), a call-by-value `Eval` semantics (`bendtt.lean:1677-1702`), and the top claims: `Claim.consistent` (no checked def has type `Empty`, `bendtt.lean:1710-1712`), `Claim.sound`, `Claim.confluent`, `Claim.sr` (subject reduction), `Claim.progress`, `Claim.halts` (live evaluation terminates, no types needed) and `Claim.empty`.
  - **PROOF** (lines 1740–3981): the lemmas proving those claims, ending in `theorem progress` (`bendtt.lean:2857`), `theorem halts` (`bendtt.lean:3962`) and `theorem consistent` (`bendtt.lean:3972`), the file's final theorem.
  - The file's own header (`bendtt.lean:3-13`) states its scope precisely: "BendTT is Bend's kernel... This file holds the whole kernel and the argument for its consistency." It is a soundness proof for Bend2's own type theory, not a bridge to any external formal system. A full-file grep for `EVM|Solidity|Yul|bytecode|Ethereum|smart contract` found no matches.
- The guide confirms Bend2 has no tactics: "Bend has no tactics: a proposition is a type, and a proof is a def of that type." (`guide/GUIDE.md:334`), matching the "no tactics yet" premise in this task's background.
- Lean is used only once, to build a native `bendtt` executable from `bendtt.lean` (cached by source and Lean-version hash); every subsequent `--verdict` check runs that native binary and needs no live Lean (`CHANGELOG.md:375-381`, 2.0.30 entry, and confirmed independently by a past session that stripped Lean from a sandbox and re-ran a cached kernel successfully — session `01a162aa-6ca3-71fc-be3b-03460bb00208`, message `c7e40a5c`, 2026-10-24).
- No file in the Bend repository, and no upstream issue, mentions Stele, EquiVM or EVMLean. The connection the background's "shortcut" proposes — exporting Bend2 definitions as BendTT terms that Lean checks, then connecting to EquiVM/EVMLean in Lean — exists only halfway: the `-o x.bendtt` export (`bend2/safe.ts:1605-1640`) and the `bendtt.lean` kernel check it against are both real and working. The second half, a formal connection from BendTT's own `Term`/`Typed`/`Eval` to Stele's `ContractDecl`/semantics, exists nowhere.

### (c) Routes to verified bytecode

Every route must supply the three parts the coordinator named: an emitter, either a verified emitter or per-contract translation validation, and the symbolic-to-concrete hash step that Armada's Dolev-Yao model needs. None of the routes below removes all three; they differ in which parts they reuse.

**Route 1 — the route already in progress (no Bend2): Lean model → Stele → EVMLean, all in Lean.**
Already scoped in `engineering/build-plan.md:119-127` (S5, "operator rulings 2026-10-25"): "The Lean model (`AFDudley/armada-lean`) is a symbolic (Dolev–Yao) specification... A Stele specification... gives the same contract with concrete values... A new refinement proof shows that the Stele specification implements the Lean model... No existing tool provides this proof... The bytecode runs on EVMLean... EquiVM proves that the bytecode refines the Stele specification." What exists: armada-lean's adjudicator model (40 theorems, `armada-lean`'s `docs/nitro-theorems.md`), EquiVM's existing refinement machinery and reasoning library (`EquiVM/Stele/Refine.lean`, `EquiVM/Reasoning/`), and EVMLean's EVM semantics, all three already building on Lean toolchain v4.33.1 (session `01a164c6-6191-72ba-ac6d-f8cf841e9331`, 2026-10-26, `.scratch/lean-v4.33.1-report.md`, confirms the bump to EVMLean `bcca6b1` and EquiVM's toolchain match, consistent with the commits `3defd676`/`bcca6b14` given in this task). What is missing: the Lean-to-Stele symbolic-to-concrete refinement proof itself, which the build plan calls novel. **Size [INFERENCE]:** no Bend2 work at all; the missing proof is the only new artifact, and its difficulty is native to Armada's symbolic model, not to any compiler target — likely comparable in effort to one of EquiVM's existing LLM-assisted Benchmark-scale proofs (MakerDAO Dss, WETH9, OpenZeppelin contracts per `EquiVM/README.md:13-17`), plus whatever extra reasoning the Dolev-Yao-to-concrete step needs, which has no precedent in EquiVM's current case studies.

**Route 2 — Bend2 emitter, proved only inside Bend2/BendTT, no Lean bridge.**
Parts: (a) re-express the armada-lean contract model as Bend2 `Evm.bend` contract code; (b) prove Bend2 laws mirroring armada-lean's 40 adjudicator theorems, checked by `bend --verdict` (BendTT), not by Lean; (c) emit Yul/bytecode via `bend-evm`. What exists: `bend-evm`'s emitter and its "contract ≡ IR" and "IR ≡ Yul model" proofs (see §b). What is missing: (i) bend-evm has no symbolic Dolev-Yao hash model, so Armada's Poseidon/Keccak-as-distinct-terms reasoning has no home in it — this would need new work inside bend-evm itself, duplicating Route 1's hard part; (ii) the "tested, not proved" boundary (printer, `solc`, Yul-model-vs-real-EVM) stays open regardless; (iii) a BendTT-checked proof is a different trust artifact from a Lean-checked one and cannot be cited inside an EquiVM certificate or `#print axioms` audit without a translation that does not exist (see Route 3). **Size [INFERENCE]:** large on its own terms — `bend-evm` took 27 roadmap milestones to reach its current ERC-20/AMM/WETH/auction coverage, has no loops or contract-creation support yet (M28–M30 open), and even finished would deliver a result the existing Armada verification chain cannot consume without Route 3's unbuilt bridge. Not a shortcut over Route 1; it adds work.

**Route 3 — the coordinator's proposed shortcut: Bend2 → BendTT → Lean, then connect to Stele/EVMLean in Lean.**
Parts: (a) `bend --verdict -o x.bendtt` already exports a Bend2 proof as a BendTT term (exists, see §b); (b) `bendtt.lean`'s kernel already checks it in Lean (exists); (c) a new formalization connecting BendTT's `Term`/`Typed`/`Eval` to Stele's `ContractDecl`/semantics, proving the translation preserves execution, so a BendTT-checked Bend2 proof becomes usable evidence inside an EquiVM-style Lean certificate. Part (c) exists nowhere in either project (confirmed by the grep and search in §b). A past session assessed the mirror-image problem — lifting a Lean tactic proof's term into BendTT — and found it hard for structural reasons that apply symmetrically here: "Lean tactics freely use `propext`, `funext`, `Quot.sound` and `Classical.choice`... BendTT has none of these"; "A Lean proof cites Lean's own lemmas about Lean's own types... Each of these has to be mapped onto the Bend2 definitions it stands for, or the lifted proof is about the wrong objects"; conclusion, "reconstruction from Lean is a research project in its own right" (session `01a162aa-6ca3-71fc-be3b-03460bb00208`, message `167c532b`, 2026-10-25). The same session separately confirms the asymmetry does not make the forward direction free: Bend2's own labbook decision states "Lean is for targets whose code cannot carry its own proofs, such as Solidity," treating Lean-side Stele specs and Bend2-side BendTT laws as two different, non-interchangeable proof substrates by design (`docs/labbook/bend2-for-the-core-and-lean-for-the-specs.md`, decisions 2–4, quoted via session `01a162aa-6ca3-71fc-be3b-03460bb00208`, read 2026-10-25). **Size [INFERENCE]:** largest of the four routes — a new verified-compiler-style correctness proof between two independently designed formal systems, with no reusable precedent in either codebase; months, not the "quick connection" a shortcut implies.

**Route 4 — treat Bend2 as one more EquiVM source language (smallest route, but does not remove Armada's missing proof).**
EquiVM's Stele is explicitly "source-language agnostic" and "not implemented by any compiler" (`EquiVM/README.md:25-31`); a Stele spec is ordinary Lean text, hand-written or LLM-drafted against the Solidity source today, and the README states directly: "LLMs can also be used to draft the Stele specification, or to audit its semantic faithfulness against the bytecode before attempting a proof" (`EquiVM/README.md:151`). Under this route, a Bend2 contract compiled through `bend-evm` is treated exactly like a Solidity or Vyper contract already is in EquiVM's existing workflow (`EquiVM/README.md:14-17` lists Vyper proof-of-concept support): draft a Stele spec for it (optionally informed by `bend-evm`'s own `LAWS.bend`/`IR` as a human- or LLM-readable reference, not as a formal input) and run EquiVM's standard per-contract refinement proof against the compiled bytecode, using EquiVM's existing reasoning library and tactics. This needs **no new bridge code or new formalism** — it reuses 100% of EquiVM's trust chain (Lean kernel, EVMLean semantics, the three standard Lean axioms) — at the cost of not reusing any of `bend-evm`'s own BendTT-checked proofs, which become a differential-test aid rather than part of the certificate. For Armada specifically, this route still leaves the Lean-to-Stele symbolic-to-concrete refinement from Route 1 unaddressed, because that proof is about armada-lean's Dolev-Yao model, not about which language emitted the bytecode; Bend2 would only change how the bytecode and an ordinary (non-symbolic) Stele draft are produced, not how the symbolic layer connects to it. **Size [INFERENCE]:** smallest machinery addition of the four, but it answers a different question than Armada's; it is a way to get *a* verified contract from Bend2 through EquiVM, not a way to shorten Armada's specific missing proof.

### (e) Open questions

1. Is a BendTT-checked proof (Route 2/4) an acceptable trust tier for Armada at all, given the project's existing standard is a Lean-checked EquiVM certificate with a named, audited axiom footprint? No prior session or document states a position on mixing proof kernels within one contract's trust chain.
2. If Route 4 is taken for a future Bend2-authored contract, does `bend-evm`'s own BendTT proof reduce the human/LLM effort of drafting the Stele spec and completing the EquiVM refinement proof, or does writing the Stele spec from scratch (as for Solidity today) cost the same regardless of the source language? No case study exists either way.
3. Does Armada's Dolev-Yao symbolic hash model (`ArmadaLean.Poseidon.Term`, per `armada-lean`'s trust-base section) have any natural encoding inside `bend-evm`'s current concrete-Keccak model, or would a Bend2 route need its own new symbolic extension to `bend-evm`, duplicating Route 1's hard part in a second language? Not investigated here; `bend-evm`'s roadmap (M1–M27 read in full) shows no symbolic-hash milestone, planned or done.
4. `bend-evm` and `bend-frontend` are third-party forks (`ind-igo`), not evaluated here for maturity, maintenance, or independent audit beyond their own stated roadmap and test suite. Their trust claims (README "Certificates"/"Lowering" sections) were read, not independently re-verified by running their proofs or tests.
