# EquiVM, EVMLean and lean-mend: audit, port state, and the toolchain question (2026-11-02)

Context: the deposit refinement slice (`docs/process.md` "The next chart"; `engineering/build-plan.md` S5) needs
EquiVM to prove that Armada bytecode refines a Stele specification. Before any of that work, the coordinator
measured what we would build on. Every fact below has its command or file; unmeasured claims are marked
`[INFERENCE]`.

## 5. Compilers

EquiVM proves a theorem about bytecode, so the compiler is not trusted and any compiler works in principle. In
practice the proof automation recognises one compiler's code shapes (`Reasoning/Solc.lean`: `solcDispatchReachBody`,
`solcGuardPrologueRD`, `solc_dispatch_prefix`, via-IR helpers). Another `solc` version, optimizer setting or EVM
version can change those shapes `[INFERENCE: extent not measured]`. Solar (paradigmxyz/solar) now generates bytecode
(Solidity, MIR, EVM IR, bytecode; `forge build --use solar`) but its README says "Please do not use it in production
environments", and its code shapes differ from solc's, so it would need its own automation package.

## 7. The toolchain question (operator, 2026-11-02)

Operator: "it seems like this all needs to be converted into more of a toolchain than a tool. the aggressive
versioning of lean and the vintages vs versions of solc implies we'll regularly need to rebuild stuff if the intent
is a general purpose tool."

Proposal (coordinator; design, not decided):
1. A vintage is one pinned tuple: Lean toolchain, Mathlib and Batteries, EVMLean, EquiVM, `solc` version and
   settings, target hardfork. Every proof names its vintage.
2. A certificate per vintage: theorem statements and axioms (lean-mend's baseline and after certificates). A move
   between vintages is accepted only when they are equal.
3. Split the stable layers (EVM semantics, Stele, the refinement relation) from the version-bound layer (the
   compiler-shape automation), one package per compiler vintage.
4. Regenerate every generated artifact from the vintage: bytecode from the pinned compiler, block summaries
   (`generate_rd_blocks.py`), Spec and Witness files (`convert_spec.py`).
5. One rebuild pipeline per bump: lean-mend's rules first, the residue to an agent; a compiler bump regenerates
   bytecode and summaries.
6. Gates that run: the full build including Benchmarks, EVMLean conformance, `stele-difftest`, the certificate
   comparison, and an axiom census that counts `native_decide`.
7. Choose vintages; do not chase every release.

Operator ruling, 2026-11-02: "we should make a new monorepo for this work. at first the goal is to support the
armada work, but we need to be general purpose in the future." So the toolchain is one new repository. It serves
Armada first (one vintage is enough at the start) and is designed so that it can later hold several vintages and
serve other projects. EquiVM, EVMLean and lean-mend move into it; the way they move in (git subtree with history, or
a fresh import) is still to decide.

Still open for the operator: whether `native_decide` is accepted in the EquiVM layer as a stated assumption.
