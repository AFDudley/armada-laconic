## 3. Procedure for a pebble

1. Read the target tool's documentation before you file or run anything. For exophial, read `docs/AUTHORING.md` §1.1.
2. File with `exophial intake` as a defect report: the promise that is broken, what holds now, how anyone can observe
   it, and the constraints. State no cause, mechanism or remedy, and name no script or file to create. Check with
   `--dry-run`, then file. Then `exophial pebble estimate <id> --points N`.
3. File only on an explicit operator order. A question is not an order.
4. Before you file, search the target repo's bus for a duplicate, and state the search scope of every absence claim.
5. Review the derived spec before any worker starts. A spec is graded from the base commit. A comment added after
   derivation does not change the spec; close and file again instead.
6. An operator-known change that touches no `scripts/`, `tests/` or `contracts/specs/`: commit on a branch in a
   `.scratch/` worktree, then `TMPDIR=$PWD/.scratch exophial apply <branch> --title ... --reason ...`.
7. A parked pebble goes to a husband subagent under `exophial/scripts/husband/husband.md`, never an unchanged unpark.
   The brief forbids `git stash`, pre-built artifacts that make a check pass, fallbacks and retry loops.

## 6. Designs discussed, not written

### 6.1 Treasury fees and the deposit system

- **Observed in armada-poc** (`contracts/privacy-pool/modules/ShieldModule.sol` lines 193–219 and 323–360): on every
  shield that is not from a registered adapter, the module transfers the fee to the `treasury` address as a plain
  ERC-20 transfer, in the shielder's own transaction. The integrator fee is paid the same way.
  `contracts/yield/ArmadaYieldVault.sol:391` pays the yield fee (10%, or 15% when `ArmadaFeeModule` is connected; the
  maximum is 50%) with `safeTransfer`. `ArmadaTreasuryGov` holds plain ERC-20 balances under a `TimelockController`.
- **Consequence:** a shield from a tainted address sends a direct transfer from that address to the treasury, so the
  treasury is one hop from tainted funds. The yield fee comes from the vault's pooled position and links to no user.
- **Idea discussed:** the shield path creates a fee note for the treasury instead of a transfer. The treasury would
  then need a spending key. FROST could share it, but the hubs' FROST is secp256k1 with Keccak-256
  (`frost-secp256k1-evm` 3.0.0); a note spend needs EdDSA on BabyJubJub with Poseidon. That needs a new `frost-core`
  ciphersuite. The `nullifyingKey` and the viewing key cannot be split with a threshold signature (MPC proving or
  threshold ECDH would be needed). Governance limits (outflow limits, steward budgets, wind-down sweep) would not apply
  to shielded funds.
- **Operator position (2026-10-16):** the coupling between the deposit system and the treasury is bad architecture.
  The design needs more discussion before any ADR or code.

### 6.2 How a hub tracks cross-chain swaps

- The design (`engineering/shielded-nitro-bridge-design.md` §4–§6, ADR-0015) declares hub inventory, rebalancing and
  pricing "out of protocol", at most an open-source "reference hub daemon". No such daemon or design page exists.
- A cross-chain swap uses one channel on each chain, each with one asset, linked by a hash lock (go-nitro
  `HashLockedSwap.sol`: single asset, two parties). A single-chain swap is one co-signed state of one channel with two
  assets (ADR-0017).
- What a hub would have to track [INFERENCE]: the latest co-signed state of each channel on each chain; each swap as a
  pair of conditional payments with its hash and whether the secret is revealed, so it claims the second leg before
  the challenge window ends; its inventory and promised amounts per asset per chain; its net imbalance between chains;
  and every open challenge against its channels on both chains.
