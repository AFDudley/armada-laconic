# The K framework and Runtime Verification: survey against the planned Lean 4 DSL

Scope: K framework core, KEVM, K Solidity semantics, Kontrol, RV's Lean 4 work
(`klean`, `evm-equivalence`), RV's ERC-20/contract specifications, RV protocol
audits with a state-machine model, and `act` (the specification language from
the K/KEVM lineage, now at `argotorg/act`). Cardano is out of scope; a separate
agent covers it.

A claim with no citation below did not come from a primary source I read; it
carries `[INFERENCE]`.

## Summary verdict

**None of these tools provides the planned DSL.** Armada's `machine`
(invariant-carrying state type, generated preservation and can-happen
obligations), `contract` (Solidity AST plus bytecode proof per compiler
profile), and `implements … via` (generated refinement obligations) have no
single match. Two design ideas are worth copying, both named in the table's
last column. Everything else is at most a design precedent, read once and set
aside, matching labbook `2026-11-20-temper-and-the-dsl.md` §2's finding about
Isabelle, Rocq and HOL4: no other system has this project's four-layer split.

## What to copy, and from where exactly

1. **The "automated bytecode-equivalence leg plus proof-assistant-export leg from one declaration" split**, from `act`'s architecture (`argotorg.github.io/act`, "act Verification Pipeline" diagram and the HEVM/Rocq backend descriptions). Armada's `contract` + `implements … via` already has this shape independently (Blanc for bytecode, Lean itself for the gluing-invariant refinement), so this is confirmation of an existing design choice, not a new mechanism to adopt.
2. **"Prove the proof is about one build's bytecode, not about the compiler"**, from KEVM and Kontrol's documented practice (not a quote, but every proof artifact cited above is over one `.sol.json`/one Foundry build's bytecode, never over solc). This matches `docs/process.md`'s existing ruling that solc is untrusted and the theorem is per-build (§"The layers", row Implementation; §9.1).

No other construct is transferable. In particular, `klean`'s K-to-Lean code generation does **not** give Armada a usable Lean EVM semantics: it is heavily axiomatized (73 axioms in generated code per `evm-equivalence`'s own count) and RV itself treats it as untrustworthy enough to require a separate equivalence proof against Nethermind's independently hand-written `EvmYulLean`, which Armada's own `2026-11-20-temper-and-the-dsl.md` does not reference and which is outside this survey's RV-only scope.
